# U-INT-4 · Who computes every number

**For** task 3's contract of the scoring runner, and task 2's gates that read its numbers. The terms and the cross-cutting rules IR-32 to IR-40 are in the [index](../blocking-decisions.md) [ours].

**Status:** third version, 2026-10-02, after the closure checks, applying C-1 to C-14 and the Codex gate's four findings; this file applies C-1, C-4, C-6, C-7, C-8 and C-10 [ours]. **From the second version, after the wave-1 review, it also applies:** F-2, F-8, F-15, F-16, F-17, F-19, F-22, F-24, F-27, F-28, F-32, F-33, F-35, F-41, F-42, F-43 and F-45, and the parts of F-1, F-3, F-6, F-7, F-9 and F-11 that bear on U-INT-4; and the coordinator's amendments A2 (costs as usage, not bills), A4 (job arguments) and A5 (C_base's hash check) [ours].

## 1. The choice

- **IR-1 · The scoring runner computes every number about a row's performance.** [ours]
  - IR-1.1 Every number about a row's performance that a decision in the loop reads, or that a manuscript, a results table, a gain or a report gives, is the value of a released result record (IR-33), or a deterministic function of such values that engine code computes, such as a gain, a mean or an interval: for E_base, C_base, candidates, engineering rounds, ablations, A_FullEng refinements, rebuttal rows and controls alike [ours].
  - IR-1.2 Agent code computes none of them; a number that agent code computes has no standing in a decision or a report [ours].
  - IR-1.3 A number from G's paper is quoted only from the manifest, labelled as published, never as a row of the run [ours].
  - Scope: a number that is not about a row's performance, such as ScholarPeer's review score against its threshold of 8, or the novelty scores the seed ideas are sorted by, is outside IR-1; it is a model output that engine code records [App. A.2] [§3.1] [ours].
- **IR-2 · What agent code hands over.** [ours]
  - IR-2.1 Agent code hands the runner a code tree at a content hash, whose entry points follow the manifest's interface: fit and predict, or one solution function [ours].
  - IR-2.2 Nothing else reaches a harness job from an agent: never a score, a metric, a split, data, a prediction made outside a harness job, or an artifact that IR-3.2 does not name [ours].
  - IR-2.3 The runner and the scoring items read no parameter from the code tree. Every scoring parameter (a threshold, a rendering option, a sample size, a setting) is a hashed scoring item, and the metric step receives from agent code only the outputs of its predict step. The job arguments that engine code reads from switches the code tree declares, such as task 2's mechanism switches, reach only the agent's own entry points, never a scoring item (IR-32.1) [ours].
- **IR-3 · Lineage: where a scored artifact comes from.** [ours]
  - IR-3.1 The runner scores an artifact only if a fit job that the runner ran and recorded produced it, from the same code hash and job arguments, with a seed it passed from the role's seed list (IR-10.2), without network [ours].
  - IR-3.2 A fit job reads only: the data its kind may read (IR-11); weights the manifest pins with their hashes; and artifacts of other recorded jobs, named by hash, whose own lineage is recorded. Its record lists every input by hash, and that list is its lineage [ours].
  - IR-3.3 When the runner hashes a code tree (IR-2.1), it refuses the tree if it holds an array file (by format or extension), a binary file (any file that is not UTF-8 text) or a file above the manifest's per-file size bound, unless that file's hash is the hash of a pinned weight or of a recorded job's output. It also refuses the tree if the total size of its content that is neither in the pinned commit, nor a pinned weight, nor a recorded job's output, exceeds the manifest's tree bound, so that weights split into many small text files (base64 chunks, or literals spread across modules) are refused as one file would be. A refused tree is logged and handed to G2. Task 5 sets both bounds per task, the tree bound from the size of the code the task's ideas need; what they cost a method: a large data file it built itself must be built by a recorded job instead. Weights hidden in source text below the tree bound remain detection only, by G2 and I2 [ours].
  - IR-3.4 External weights that a method or a rebuttal needs, such as a pre-trained backbone or a second foundation model, enter only through the manifest: packaging pins each with its source, version and hash, after a person has screened it for exposure to the task's report data. During a run there is no acquisition job; a request for weights the manifest does not pin is refused and recorded, and the rebuttal task that needed them is reported as not run [ours].
  - IR-3.5 A reused checkpoint: a row that builds on another row's fitted artifact, such as a post-hoc method on the baseline's backbone, has its fit job read the recorded artifact of that row (E_base or C_base) at the same seed, so that the two share the upstream checkpoint per seed and their comparison stays paired. At the test event that artifact is E_base's report fit for the same report seed (IR-14.4) [ours].
  - IR-3.6 The seed flag: with s seeds, a row whose variance across seeds is below the 1% quantile of F(s−1, s−1) times the baseline's variance across the same seeds is flagged to G2. For s = 5 the quantile is 0.0626, a ratio of standard deviations below 0.25. The flag detects; a partial seed game escapes it. In a run, every row is compared with one estimate of the baseline's variance, so the flags of honest rows are correlated: the research-engineer's closure check simulates a 0.045 chance that 5 or more of 100 honest rows are flagged, where independent flags would give 0.0034. A flag is therefore read row by row, never as a rate across rows [ours].
- **IR-4 · The baseline is the task's own code.** [ours]
  - IR-4.1 E_base is the task's code at the commit the manifest pins, plus the packaging diff the manifest records. The diff is fixed outside any engine run, and a person signs it off, with the sign-off recorded in the manifest; whether an assistant helps write it is not this rule's concern. What it guards: no engine agent, and nothing a run's search produces, shapes the baseline's code [ours].
  - IR-4.2 E_base's fit jobs and its search scoring run at admission, with task scope, keyed on the baseline key, before any run of the task can be registered; runs refer to these records by ID and never write them. This settles the E_base half of A-BASE-1: once per task [ours].
  - IR-4.3 C_base, the copy that ideas start from, which the Baseline Coding Agent prepares, is scored as a row in each run before any idea is scored, and frozen as a control (IR-14.3), unless its code hash equals E_base's (the pinned commit plus the packaging diff), in which case E_base's records stand for it. The runner checks the equality when the run starts. Task 2 keeps C_base as the pinned code unchanged (amendment A5), so this check makes the rule hold by construction. When C_base is scored, the verified table shows ours − C_base beside ours − E_base, and a C_base − E_base difference on search outside the baseline's seed noise, by a paired t-test over the shared search seeds at two-sided α = 0.01, is flagged in the ledger before any idea is scored, and shown in the reported table [§3.2] [ours].
- **IR-5 · Only the runner writes a result.** [ours]
  - IR-5.1 A result record is append-only and written by the runner only; every consumer rejects a record the runner did not write [ours].
  - IR-5.2 A record holds: its result ID; its identity (IR-32.1); the run ID, or the task or audit scope; the manifest hash and the baseline key; the row's role and ID; the code hash and job arguments, or E_base's pinned commit; the fit job's ID, its artifact hash and its lineage (IR-3.2); the split role and its index hash; the attempts and their causes (IR-33.3); the metric's name and direction; the value per setting and seed, with the manifest's aggregate and spread; the engine commit and the scoring items' hashes; the environment digest and machine configuration; the status (ok, invalid output, failed, timed out); its times and compute used; and the hash of its stored per-item outputs (IR-5.5) [ours].
  - IR-5.3 A job writes to the store and ledger of the scope that asked for it: task scope for admission jobs (E_base's search and report fits and scorings, the sealed check), run scope for a run's search fits and scorings, its test event and its correction events (IR-41), except E_base's corrected records, which are task scope (IR-41.2), audit scope for the audit's re-fits (IR-36). No agent process has a write path to any store or ledger; a refused write is logged and handed to G2 [ours].
  - IR-5.4 A session reads, of the records, only the aggregates per setting and seed of search records that engine code hands it, never per-item outputs. Who chose this cut: task 6. What it loses: per-item error analysis on search, which stays available on the validation part of fit [ours].
  - IR-5.5 Per-item predictions and raw judge outputs are stored, hashed in their record, and readable by engine code and the audit only [ours].
  - IR-5.6 The run ledger closes when the run ends, whatever its end state (exported, ended without a freeze, ended in IR-39.3's end state, or halted), and nothing is appended to it after; a correction event (IR-41) appends to a correction ledger of run scope [ours].
- **IR-6 · The runner, the scoring items, and their hashes.** [ours]
  - IR-6.1 The scoring runner is engine code, the same for every task, and enforces IR-5, IR-6.3, IR-9.2, IR-11, IR-13 and IR-14. A task's scoring items (data loaders, output schema, metric and its direction, aggregation, environment image, a judge's configuration, a rollout environment) are hashed in the manifest and run by the runner [ours].
  - IR-6.2 Before any run, the manifest records the hash of: each scoring item; the index files of every role; the labels; E_base's commit and diff; the pinned weights; the seed lists; the machine configuration of a time metric; and the task rules [ours].
  - IR-6.3 The runner checks every hash a job depends on at the start of every job (hook G1). The check is made by the runner, never by an item it checks [ours].
  - IR-6.4 A change to the runner is a change of engine version, and so of the configuration hash (IR-18.3), never of a manifest. A change to a scoring item is a new manifest version, and changes the baseline key (IR-15.2); a correction's manifest version inherits the task's admission (IR-41.5) [ours].
  - IR-6.5 On a mismatch, the runner refuses the job and releases nothing, and the run halts with its class (IR-35). No agent session can write a hashed item; sessions can read the scoring items' code and the task rules, never the index files or the labels [ours].
  - IR-6.6 On a change to the runner, E_base is scored again on search under the new runner, with no read of report, and compared with its admission records. That re-scoring is a job of its own kind, a runner check, whose identity carries the new runner's version (IR-32.1), so it executes rather than returning the admission record; a re-admission is identified by the baseline key and the new runner's version, and is released once for each pair. The records are kept only if the two agree within E_base's seed noise on search; otherwise the change moves values, and the task is admitted again under the new runner (IR-15), a re-admission that counts as an attempt against k (IR-15.5), so that no gain mixes two runner versions [ours].
- **IR-7 · Gates read released numbers, and an LLM can only be stricter.** [ours]
  - IR-7.1 Every gate whose pass condition is about performance (better, outperforms, strictly superior, a clean breakdown) has a numeric precondition written as data: a value of the assessor parameter of the stage primitive (IR-40), over released records, naming the metric, the settings, the margin and the seeds. Task 2 sets each value (U-SUB-1, U-SEL-1, A-ABL-3, U-ABL-5) [ours].
  - IR-7.2 An LLM verdict may fail a candidate that the precondition passes, and never passes one that it fails [ours].
  - IR-7.3 Agent-written text (logs, reports, comments, code) may be shown to an LLM critic; no operand of a precondition comes from it [ours].
  - IR-7.4 Each number in a critic's recorded rationale is matched against the records it cites, and a number that matches none is flagged in the ledger [ours].
  - Not decided here: what a three-verdict critic does when its precondition fails. The system-architect review proposes that `Good` becomes `Engineer` while budget remains, and `Bad` after that; this goes to task 2 as a proposal for U-SUB-1 [ours].
- **IR-8 · Metrics that are not a function of predictions.** [ours]
  - IR-8.1 Time and throughput: the runner measures the compared rows in one job, interleaved, on the manifest's machine configuration, which names the hardware class and the settings that move timings (frequency scaling, simultaneous multithreading, address-space randomisation), and records every repeat. The repeat count is ⌈2(3σ/δ)²⌉, where σ is the standard deviation of one repeat measured at packaging and δ the smallest difference between two rows that task 5 wants resolved; the factor 2 is there because the difference of two rows carries the noise of both. At the test event E_base is timed again in the same job as the frozen rows (IR-14.4). A time that agent code reports is never a result [ours].
  - IR-8.2 A metric from an LLM judge: the judge's model, version, prompt, sampling and input-rendering code are scoring items; the runner makes the manifest's k calls per item and stores every raw output (IR-5.5) [ours].
  - IR-8.3 Returns from rollouts: the runner runs the environment it holds, on the episode seeds of the job's role, which are disjoint across roles (IR-10.2), for the manifest's episode count; agent code supplies only the policy [ours].
  - IR-8.4 A metric that cannot meet its clause is not reportable, and a task whose headline metric cannot meet it is inadmissible [ours].
- **IR-9 · Every setting, every seed, valid outputs only.** [ours]
  - IR-9.1 A result covers every setting the manifest lists for its split, and the whole index of each; agent code chooses neither the settings nor a sample of them [ours].
  - IR-9.2 The runner validates every output against the output schema (shape, type, range, no NaN) before the metric step; an invalid output is released as an invalid result [ours].
  - IR-9.3 Every reported row is fitted and scored at every seed of its role's list, one list per role, shared by all rows. A list holds at least the manifest's seed floor, which task 5 sets from measured noise and never at 1. Gains are computed per seed pair, then aggregated [ours].
  - IR-9.4 A row's aggregate covers every seed and every setting. A failed, invalid or timed-out seed or setting makes the row's aggregate invalid; it is recorded, never dropped [ours].

## 2. The attacks these rules stop, with the evidence

- **Agent-computed numbers, checked against themselves.** The trace's script extracts the features, scores both methods and writes the report [p. 42] (image). The one audit shown re-ran that script and found every number equal to the report's, the ablation table included: "CIFAR-100 ID top-1 = 92.95%, non-uniform Fisher weights, and the ablation table all match" [p. 47]. Table 7's first row passes score verification 50/50, although one of its codebases contains reward hacking [Tab. 7] [fn. 2]. Stopped by IR-1, IR-2 and IR-5 [ours].
- **The weak baseline.** The trace's summary states both gains: average FPR95 improves by 1.99 pp over the reproduced X-Mahalanobis and by 1.58 pp over the published number, because the in-script baseline trails the published one, 4.17 against 3.76 [pp. 41–42] (image) (paraphrase). The reproducibility audit says "Per the requirements, I only audited the Ours method (not the baseline)", although the same page reports that the ablation table matches, and that table's first row is that baseline [p. 47] [p. 41] (image). The specification audit called the in-script baseline faithful from reading the code [p. 50] (image). Stopped by IR-4 [ours].
- **Side changes in the adaptation.** Ideas start from C_base, which the Baseline Coding Agent prepares [§3.2] (tex:sections/3_new_method.tex:37). A training change made there reaches every candidate and every ablation row, which then cannot attribute it: the class of change that App. B says carried a rejected TeCh variant, whose gains came from "general training controls (EMA and label smoothing)" [App. B] (tex:sections/appendix.tex:223-224). Stopped by IR-4.3 [ours].
- **Weights with no provenance.** The trace's method is post-hoc on the baseline's fine-tuned checkpoint, trained at one seed, and its ablation reuses that checkpoint and the features the final script cached [p. 40] [p. 45] (image) (paraphrase). A rule that admits the code tree's files lets an agent place there weights tuned outside any recorded job, such as the best of many sandbox seeds, and a re-fit then reproduces them exactly. Stopped by IR-3.2 and IR-3.3; the legitimate reuse is IR-3.5 [ours].
- **External weights.** The one rebuttal shown runs on a second, frozen foundation model, TabPFN v2, whose checkpoints come from its vendor's package [p. 51] (image) (paraphrase). TALENT notes that general tabular models are often early-stopped on a validation set of real-world datasets, and reports that TabPFN v2's validation set overlaps 27 of TALENT's 300 benchmark datasets, so public weights can carry the benchmark's own data ([TALENT, arXiv:2407.00956v4](https://arxiv.org/abs/2407.00956v4), its JMLR appendix, fetched with curl on 2026-10-02). Stopped by IR-3.4, with a person's screen [ours].
- **Tampering with the evaluator.** On T-SAE, AutoSOTA's winning edit "changes how tokens are shown to the LLM judge", a configuration value that App. B calls "a threshold in the evaluation harness", and the paper concludes that "The AutoSOTA gain lives in the evaluator, not the model" [Tab. 16] [App. B] (tex:sections/appendix.tex:306-312) (tex:sections/appendix.tex:208-209). In ScientistOne's audit, solvers held "a hyperparameter tuning loop gated on an environment variable that is set differently during canonical re-evaluation", and agents went on to "import the evaluator and build its own tuning loops" [Ref: meng2026scientistone §6.1] (ref:2605.26340v1:sections/06b_integrity.tex:48) (ref:2605.26340v1:sections/06b_integrity.tex:54). Stopped by IR-2.3, IR-3, IR-6 and IR-8 [ours].
- **Choosing the data that is scored.** The report titled FULL covers the six OOD sets of the balanced CIFAR-100 setting [p. 40] (image); CIFAR-100-LT, on which an earlier variant failed at 79.89% AUROC, is absent from it [p. 46]. That CIFAR-100-LT is a setting of this task's benchmark is an external fact, from the X-Mahalanobis paper (artifacts.md, A-ART-12). The rebuttal ran on 50 TALENT datasets it chose, with test sets capped at 2000 rows [p. 51] (image), a choice no stage of §3 defines [§3.5]. Stopped by IR-9 and IR-10 [ours].
- **Agent prose steering a critic.** The trace's report says every component contributes, and justifies it by the near-OOD gain: CIFAR-10 AUROC rises from 95.91 to 97.18 and then 97.58 as two components are added, while the six-set average AUROC falls from 99.16 to 99.07 and then 99.02 [p. 41] (image) (paraphrase). ScientistOne found a paper whose "fabricated metric direction" made the worst result read as the best [Ref: meng2026scientistone §6.1] (ref:2605.26340v1:sections/06b_integrity.tex:40). Stopped by IR-7, and by IR-5.2's direction field [ours].
- **Time and judged scores.** ScientistOne left one task out of score verification because its score has "an execution-time component that varies with hardware" [Ref: meng2026scientistone §6.1] (ref:2605.26340v1:sections/06b_integrity.tex:13). VD-STrans's gain is a throughput gain, and to remove measurement noise its paper pins execution to one NUMA node and disables Hyper-Threading, Turbo Boost and address-space randomisation [p. 3]; Pinet's solution reports training 3.0× faster [Tab. 16]. Stopped by IR-8 [ours].

## 4. Roads not taken

- ⛔ WHY NOT let agent code score and audit it afterwards, as the paper does: a re-run of the agent's own scoring shows only that it is deterministic, as Table 7's first row shows, and every decision has read the agent's numbers before any audit runs [Tab. 7] [fn. 2] [ours].
- ⛔ WHY NOT let the Baseline Coding Agent produce E_base, as §3.2 does: a reproduction weakened within any tolerance inflates every gain by the weakening, as the trace's 0.41 pp does [§3.2] [p. 41] (image) [ours].
- ⛔ WHY NOT make C_base's equality with E_base an integrity rule, the system-architect review's other option: whether §3.2's Baseline Coding Agent may change the code is task 2's choice of how the stage works; the integrity rule only has to make any difference visible, and IR-4.3's hash check does so whichever task 2 chooses. Task 2 keeps C_base unchanged, so the check holds by construction [§3.2] [ours].
- ⛔ WHY NOT score C_base when its hash equals E_base's: the same code at the same seeds gives E_base's records again, up to nondeterminism, for 2s more fits per run [ours].
- ⛔ WHY NOT score prediction files that agent code writes: a file carries no provenance, cannot be re-run, and may come from a process that read labels; the runner runs the entry points itself (IR-2, IR-3) [ours].
- ⛔ WHY NOT admit weights in the code tree and list them for G2, as the first version did: G2 detects at a miss rate where a setup rule can refuse, and a re-fit reproduces such weights exactly (IR-3.3) [ours].
- ⛔ WHY NOT a recorded acquisition job that brings external weights in by source and hash during a run: an agent can upload weights it trained on whatever it could reach to a public hub and then acquire them, and the hash proves only that they are what was uploaded; public checkpoints may also have been selected on the benchmark itself, which only a person's screen at packaging looks for. What it costs: a rebuttal that needs weights the manifest lacks is not run (IR-3.4) [ours].
- ⛔ WHY NOT a harness per task: every task would re-implement the code that enforces IR-5, IR-11 and IR-14, to be verified again per task; and hashing that code in every manifest would make each fix to it a new manifest everywhere, and a new sealed check of every task (IR-6.4, IR-15.2) [ours].
- ⛔ WHY NOT let scoring read a parameter from the code tree: a scoring parameter the agent sets is an evaluator edit, as AutoSOTA's T-SAE threshold was [Tab. 16] [ours].
- ⛔ WHY NOT strip the numbers from agent text before a critic reads it: it blinds critics to hyperparameters and code, and does not stop persuasion without numbers; IR-7 removes the effect instead of the text [ours].

## 5. Relation to the paper and to the register

- **The paper: UNSPECIFIED.** No stage names a fixed evaluator. The tasks are accepted papers "whose problem specifications and codebases serve as benchmark tasks" [§4.1] (tex:sections/4_experiment.tex:16); the coders run their experiments themselves, "producing the resulting logs" [§3.2] (tex:sections/3_new_method.tex:40); and in the trace the agent's script calls the codebase's unmodified metric function, picks the data and the baseline, and writes the report [p. 42] [p. 50] (image) (paraphrase). - **Where we depart.** One bullet per departure [ours]:
